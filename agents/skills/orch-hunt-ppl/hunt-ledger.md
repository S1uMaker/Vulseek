# Hunt ledger

Shared source of truth for audit propositions. Postgres, not `/lane/ledger.md`.
Identity (`repoId`, `snapshotId`, job, task) is filled by the API from the
environment. Do not pass those fields. There is no delete.

CLI:

```bash
python3 "$VULSEEK_AGENT_HOME/skills/orch-hunt-ppl/hunt_ledger.py" <command>
```

Function commands:

- `ensure-function --file --function-name --line [--end-line]` — inserts a row with `primitives: []`, or returns the existing row without changing it. Orchestrator creates `discovered`. Hunter creates `investigating`.
- `assign-function --id --expected-revision --reason` — orch only. `discovered → assigned`.
- `list-functions [--file] [--function-name] [--state]`
- `list-primitives [--id] [--type] [--verdict] [--title]`
- `append-primitive --id --expected-revision --type` — stdin is the primitive (`id`, `title`, `statement`, optional `locations`, `context`, `gaps`). The function row must already exist.
- `set-function-state --id --expected-revision --state --reason` — hunter only. Allowed: `assigned → investigating|blocked`, then `partial|covered`, then `covered → verified`.
- Primitive updates (`append-evidence`, `set-verdict`, `update-gate`, …) take `--id` as the function id and `--primitive-id`.

There is no `changes` history. A function row revision covers every primitive on that row.

HTTP 4xx JSON (`code`, `error`, `current`) is printed on stdout; the command
exits non-zero. JSON is native JSON, never a JSON string. Times are UTC ISO
8601 (`2026-09-05T10:02:00Z`). Entry IDs are positive integers generated by
Postgres. Omit `id` on create and use the returned `entry.id` for subsequent
reads, updates, feedback, and links. JSON entry references (`entryId`,
`targetId`, `scopeHypothesisId`) must be numbers, not quoted strings.
Evidence, gap, and link IDs remain agent-chosen strings local to each row.

## Rules

- One row = one function (`file` + `functionName`), unique per snapshot.
  Propositions live in `primitives[]`. `state` on the row is function coverage,
  not a proposition verdict.
- Orch creates a function row only for a function brief (`discovered`, then
  `assigned`). Route hunts do not pre-create rows. Hunters call
  `ensure-function` for every function they analyze; those new rows start at
  `investigating`. Hunters set `partial`, `covered`, and `blocked`. Only the
  critic sets `verified`. Hunters do not `assign-function`.
- `verified` is the coverage terminal state, after `covered`.
- A primitive is one reusable statement (`source` / `sink` / `gate` /
  `connector` / `impact` / `hypothesis`). Connector and hypothesis primitives
  live on the entry function. Links use `targetFunctionId` and optional
  `targetPrimitiveId`.
- Every row has a concise `title` for human and machine lookup. The title is
  a neutral label for the proposition, not a vulnerability conclusion, and is
  immutable after creation.
- One analyzed function is one row. Do not record that function only as
  `locations` or `evidence` on another row. Skip ordinary assignments and pure
  pass-throughs. A function that was reviewed still gets a row when its result
  is a gate or an open gap.
- A gate row may describe its existence, execution, and path applicability in
  one statement with evidence and gaps. Split it only when those are distinct
  reusable statements or apply to materially different contexts. Do not cover
  a whole function with one `endLine`, but do not multiply rows solely to mark
  each reading step.
- A sensitive operation is not a vulnerability. Empty `gaps` is not proof.
- Create from `unknown` with `assessment` null. `set-verdict` only with this
  row's evidence and an assessment.
- New rows start in `discovered`. Use `set-state` to record investigation
  progress; state changes never replace evidence or verdict. Hunters primarily
  update the state of the rows they investigate.
- On `REVISION_CONFLICT`, GET the current row and retry with the new revision.
- Do not change `type`, `statement`, or `context` after create. New scene →
  new row, `related_to` the old one.
- A route in a goalPrompt is not a Ledger row. Each function on that route
  has its own row. A connector on the caller links to the callee. State,
  verdict, evidence, and gaps are never inherited through a link.

## Entry

Persisted row. `?` = optional on create; server fills the rest.

| Field | Format | Who writes | Meaning |
|---|---|---|---|
| `id` | positive integer | database only | Globally unique auto-incrementing ID. Read-only; returned after create. |
| `repoId` | string | server | Application or compose id. |
| `snapshotId` | string | server | Commit SHA, or `job:{scanJobId}` if none. |
| `type` | enum | agent on create | `source` / `sink` / `gate` / `connector` / `impact` / `hypothesis` |
| `title` | non-empty string | agent on create | Concise neutral label used for display and lookup. |
| `statement` | non-empty string | agent | The proposition. Not "maybe buggy". |
| `state` | enum | server default `discovered`; agent via `set-state` | `untracked` / `discovered` / `assigned` / `investigating` / `partial` / `covered` / `blocked` |
| `verdict` | enum | server default `unknown`; agent via `set-verdict` | `unknown` / `supported` / `refuted` / `contested` |
| `assessment` | object or `null` | `null` on create; agent via `set-verdict` | Current judgment basis. `null` iff `unknown`. |
| `locations` | `CodeLocation[]` | agent; default `[]` | Code sites. May span files. |
| `context` | `AuditContext` | agent; default `{}` | Scope: entry, actor, input, conditions, assumptions. |
| `evidence` | `Evidence[]` | server-normalized; agent via `append-evidence` | Materials for this statement. Default `[]`. |
| `gaps` | `Gap[]` | agent drafts on create or `append-gap` | Open questions. Default `[]`. |
| `links` | `LedgerLink[]` | agent via `append-link` | Relations to other entries. Default `[]`. |
| `revision` | positive int | server; default `1` | Optimistic lock. Send as `--expected-revision`. |
| `createdBy` / `updatedBy` | string | server | Current `taskId`. |
| `createdAt` / `updatedAt` | UTC string | server | |
| `changes` | `LedgerChange[]` | server | History summaries. Agent cannot rewrite. |
| `sourceJobId` | string | server | Scan job that created the row. Read-only. |

Creation rejects an agent-supplied entry `id`. Each successful create inserts
a new row. If a create response is lost, list relevant rows before retrying
to avoid duplicates. IDs can have gaps; do not predict the next ID.

### `state`

`state` tracks whether a proposition has been discovered and worked. It is
not a vulnerability conclusion; use `verdict` for that conclusion.

| Value | Meaning |
|---|---|
| `untracked` | Historical row migrated from the old ledger; it must be explicitly discovered before dispatch. |
| `discovered` | The proposition has been identified, but no Hunter is actively investigating it. |
| `assigned` | Existing or in-flight dispatch state awaiting active investigation. |
| `investigating` | A Hunter is actively investigating this proposition. |
| `partial` | Evidence exists, but a material gap remains in this proposition or its related call-chain analysis. |
| `covered` | The investigation concluded this proposition; this does not confirm a vulnerability. |
| `blocked` | Progress is blocked by an explicit reason or unresolved blocker. |

Allowed transitions are:

`untracked → discovered`; `discovered → assigned | investigating | blocked`;
`assigned → investigating | blocked`; `investigating → partial | covered | blocked`;
`partial → assigned | investigating | covered | blocked`;
`blocked → assigned | investigating`; `covered → investigating` for an explicit
reopen. Invalid transitions are rejected. `partial` requires evidence or a
gap; `covered` requires a non-`unknown` verdict and no open or investigating
gaps.

### `type`

| Value | Meaning | Example statement |
|---|---|---|
| `source` | Where input, identity, or influence enters | "filename is taken from the request query" |
| `sink` | Sensitive operation that can cause impact | "readFile uses the computed path" |
| `gate` | Check or restriction | "the route runs a login check before the handler" |
| `connector` | How data, control, or authority moves | "filename is joined, then passed to readFile" |
| `impact` | Security consequence | "files outside the download dir are returned" |
| `hypothesis` | Whole attack-scene claim | "a logged-in user can read files outside the download dir via GET /api/download" |

Same location may have several rows when the code supports distinct reusable
propositions. A connector must name a meaningful movement or change and its
from/to context; it is not a generic "function was reviewed" marker. A
hypothesis is one scene (one entry, actor, config, path). Use `connector` for
a cross-function control, data, or authority relationship, or a routing,
validation, or trust relationship observed in the code and `hypothesis` for an open end-to-end
scene. A function-local row must describe actual code behavior; do not create
a status-only placeholder merely to reserve a function location.

A route goalPrompt does not name the functions. After reading each function,
create or reuse its own row and write its evidence and gaps there. Do not
park a reviewed function on another row's evidence. Link the caller to the
callee instead of copying the callee's behavior.
Links express evidence or flow relationships, not hierarchy.

### `verdict`

| Value | When |
|---|---|
| `unknown` | Uninvestigated, insufficient, or previous judgment invalidated. `assessment` must be `null`. |
| `supported` | Evidence covers the necessary premises; no unresolved contrary material. Needs assessment. |
| `refuted` | Applicable contrary evidence against **this** statement. Needs assessment. |
| `contested` | Unresolved conflict in the same context. Needs both supporting and refuting evidence in the assessment. |

`supported` on a sink does not make a hypothesis `supported`. Blocking one
path does not refute a broader claim.

## `locations` (`CodeLocation[]`)

```json
[{ "file": "src/controllers/download.ts", "line": 12, "endLine": 14, "functionName": "downloadFile" }]
```

| Field | Format | Required |
|---|---|---|
| `file` | repo-relative path, `/` separators, no `..`, not absolute | yes |
| `line` | positive int, 1-based | yes |
| `endLine` | positive int, `>= line`; omit = single line | no |
| `functionName` | string | no |

No source site → `[]`. Do not invent line 1. Whole-array replace only
(`replace-locations`); elements have no id.

## `context` (`AuditContext`)

Object. Omit unknown members. Omission does not mean "no auth" or "all scenes".

```json
{
  "entrypoint": { "kind": "http", "name": "GET /api/download" },
  "actor": { "authenticated": true, "role": "user" },
  "input": { "name": "filename", "accessPath": "req.query.filename" },
  "conditions": ["file download enabled"],
  "assumptions": [{ "description": "the process can read the target file", "gapId": "gap-permission" }]
}
```

| Field | Format | Required |
|---|---|---|
| `entrypoint.kind` | `http` / `cli` / `queue` / `scheduled` / `function` / `other` | if `entrypoint` present |
| `entrypoint.name` | string (route, command, or function) | if `entrypoint` present |
| `actor.authenticated` | boolean | no |
| `actor.role` | project role name | no |
| `input.name` | string | if `input` present |
| `input.accessPath` | code expression | no |
| `conditions` | string[] | no; scope, not evidence |
| `assumptions[].description` | string | yes per item |
| `assumptions[].gapId` | id of a gap **on this row** | yes per item |

Do not move evidence across incompatible actor/config/path contexts.

## `evidence` (`Evidence[]`)

Each item is about **this row's** `statement`. Append only; never silently
rewrite `summary`/`ref`/`stance`. To correct: `append-evidence` a new item,
then `withdraw-evidence` the bad one.

**EvidenceDraft** (stdin for `append-evidence`; omit server fields):

| Field | Format | Required |
|---|---|---|
| `id` | string, unique in this row | yes |
| `kind` | `code` / `static_analysis` / `runtime_test` / `derivation` | yes |
| `stance` | `supports` / `refutes` / `inconclusive` | yes |
| `summary` | what the material actually shows, including limits | yes |
| `ref` | depends on `kind` | yes |
| `runId` | string | no |
| `tool` | `{ "name": string, "version"?: string }` | no |

Server adds `producer` (taskId), `createdAt`. Withdrawal is
`withdrawn: { at, by, reason }` — present means unusable for the current
verdict.

`ref` by `kind`:

| kind | `ref` |
|---|---|
| `code` | `CodeLocation` (`file`, `line`, `endLine?`, `functionName?`) |
| `static_analysis` | `{ "artifactId": string, "locator"?: string }` |
| `runtime_test` | `{ "artifactId": string, "locator"?: string }` |
| `derivation` | `{ "inputs": [{ "entryId", "revision", "evidenceId"? }, ...] }` non-empty |

```json
{
  "id": "ev-1",
  "kind": "code",
  "stance": "supports",
  "summary": "filename is assigned from req.query.filename; this only proves the source.",
  "ref": { "file": "src/controllers/download.ts", "line": 12, "endLine": 14 }
}
```

Derivation cannot input this same entry. Inputs must exist, same snapshot, and
match current `revision` or the write fails with `STALE_DEPENDENCY`.

Adding `refutes` while verdict is `supported` (or `supports` while `refuted`),
or withdrawing evidence used by the current assessment, or replacing locations,
rolls the row back to `unknown` unless the same update includes `set-verdict`.

## `gaps` (`Gap[]`)

| Field | Format | Required |
|---|---|---|
| `id` | string, unique in this row | yes |
| `question` | concrete question | yes |
| `completionCriteria` | how to know it is answered | recommended |
| `status` | `open` / `investigating` / `resolved` / `blocked` | yes; drafts start `open` |
| `owner` | string | no; not a lock |
| `taskId` | hunt/task id | no |
| `result` | string | required for `resolved` and `blocked` |
| `resultRefs` | `{ "entryId": number, "evidenceId"?: string }[]` | default `[]`; non-empty for `resolved` |

**GapDraft** (create `gaps` or `append-gap` stdin): `{ id, question,
completionCriteria?, owner?, taskId? }`. Server sets `status: "open"`,
`resultRefs: []`.

`set-gap` is explicit, not a merge:

- `open` / `investigating`: do not send result/resultRefs; server clears them.
- `resolved`: `--result` and non-empty `--result-refs`.
- `blocked`: `--result` required; resultRefs optional (default `[]`).

`gaps: []` means no questions were filed, not that the statement is proved.

## `links` (`LedgerLink[]`)

From **this** row to `targetId`. Not evidence.

```json
{ "id": "link-1", "targetId": 42, "relation": "depends_on", "reason": "this scene needs that input source" }
```

| Field | Format | Required |
|---|---|---|
| `id` | string, unique in this row | yes |
| `targetId` | another entry's integer `id` (not self) | yes |
| `relation` | `supports` / `refutes` / `depends_on` / `related_to` | yes |
| `reason` | why the relation exists | yes |
| `scopeHypothesisId` | a `hypothesis` entry's integer id | no |

`supports` / `refutes` / `depends_on` must be same repo and snapshot.
`related_to` may cross snapshots for history only. Duplicate
`(targetId, relation, scopeHypothesisId)` is invalid.
`list-sinks --unlinked-sinks` = sinks with no incoming `depends_on` or
`supports`.

Using another row as a premise also needs a `derivation` evidence item and
`assessment.dependencyRefs`.

## `assessment`

`null` when `verdict` is `unknown`. Otherwise required.

**AssessmentDraft** (`set-verdict` stdin when verdict is not `unknown`):

| Field | Format | Required |
|---|---|---|
| `reason` | why this verdict holds, including limits | yes |
| `evidenceRefs` | `[{ "entryId", "evidenceId" }, ...]` non-empty, **this row only**, not withdrawn | yes |
| `dependencyRefs` | `[{ "entryId", "revision" }, ...]` | default `[]`; every external premise actually used |

Server sets `assessedBy`, `assessedAt`. `supported` needs a `supports`
evidence; `refuted` needs `refutes`; `contested` needs both.

## CLI

The command list near the top of this skill is the current contract. The
examples below still show the previous one-proposition-per-row shapes; use
`functionId`, `primitiveId`, and `targetFunctionId` instead of `entryId`.

### Generic

| Op | Command | stdin |
|---|---|---|
| list | `list-ledger [--id] [--type] [--state] [--verdict] [--title] [--function-name] [--file] [--unlinked-sinks]` | none |
| get | `get-ledger --id ID` | none |
| create | `create-ledger` | `{ "action": "create", "entry": { "type", "title", "statement", "locations"?, "context"?, "gaps"? } }` |
| update | `update-ledger --id ID --expected-revision N --reason TEXT` | `{ "reason", "operations": [ … ] }` |

`--file` is a `locations[].file` prefix. `--title` and `--function-name` are
case-insensitive substring filters. `--id` on list is the same as get.

### Typed (daily default)

Types: `source` `sink` `gate` `connector` `impact` `hypothesis`.
List names are plural (`list-sources` … `list-hypotheses`).

| Op | Command | stdin |
|---|---|---|
| list | `list-{sources\|sinks\|gates\|connectors\|impacts\|hypotheses} [--state] [--verdict] [--title] [--function-name] [--file]` | none |
| get | `get-{source\|sink\|gate\|connector\|impact\|hypothesis} --id ID` | none |
| create | `create-{source\|sink\|gate\|connector\|impact\|hypothesis}` | `{ "title", "statement", "locations"?, "context"?, "gaps"? }` — no `id` or `type` |
| update | `update-{source\|…} --id ID --expected-revision N --reason TEXT` | same as `update-ledger` |

`get-*` / `update-*` exit `VALIDATION_ERROR` if the row's `type` does not
match. `list-sinks --unlinked-sinks` is valid. No `delete-*`.

Create example:

```bash
python3 "$VULSEEK_AGENT_HOME/skills/orch-hunt-ppl/hunt_ledger.py" \
  create-gate <<'EOF'
{
  "title": "REST author exclusion input type",
  "statement": "REST author_exclude is typed as an int array, so a string is rejected before SQL",
  "locations": [{ "file": "wp-includes/rest-api.php", "line": 115 }],
  "gaps": [{ "id": "gap-shape", "question": "Does a non-array shape skip this check?" }]
}
EOF
```

### Single-op updates

All require `--id` and `--expected-revision`. `--reason` is the update-level
reason (written into `changes`).

| Command | Extra flags / stdin |
|---|---|
| `append-evidence --id ID --expected-revision N --reason TEXT` | stdin **EvidenceDraft** |
| `withdraw-evidence --id ID --expected-revision N --evidence-id EV --reason TEXT` | none |
| `append-gap --id ID --expected-revision N --reason TEXT` | stdin **GapDraft** |
| `set-gap --id ID --expected-revision N --gap-id G --status open\|investigating\|resolved\|blocked --reason TEXT` | `--result TEXT`; `--result-refs '[{ "entryId": 42 }]'` |
| `append-link --id ID --expected-revision N --reason TEXT` | stdin **LedgerLink** |
| `remove-link --id ID --expected-revision N --link-id L --reason TEXT` | none |
| `replace-locations --id ID --expected-revision N --reason TEXT` | stdin **CodeLocation[]** |
| `set-verdict --id ID --expected-revision N --verdict unknown\|supported\|refuted\|contested --reason TEXT` | `unknown`: flags only. Other verdicts: stdin **AssessmentDraft** |
| `set-state --id ID --expected-revision N --state STATE --reason TEXT` | `STATE`: `untracked`, `discovered`, `assigned`, `investigating`, `partial`, `covered`, or `blocked`; use only an allowed transition |

`update-ledger` `operations[]` ops (same semantics, batchable in one revision):

`append_evidence`, `withdraw_evidence`, `append_gap`, `set_gap`, `append_link`,
`remove_link`, `replace_locations`, `set_verdict`, `set_state`.

Example:

```json
{
  "reason": "code check of the query-var interpolation",
  "operations": [
    {
      "op": "append_evidence",
      "value": {
        "id": "ev-1",
        "kind": "code",
        "stance": "supports",
        "summary": "author__not_in is concatenated into SQL at this line",
        "ref": { "file": "wp-includes/class-wp-query.php", "line": 2403 }
      }
    },
    {
      "op": "set_verdict",
      "verdict": "supported",
      "assessment": {
        "reason": "The cited line interpolates the query var into SQL.",
        "evidenceRefs": [{ "entryId": 42, "evidenceId": "ev-1" }],
        "dependencyRefs": []
      }
    }
  ]
}
```

## Errors

| `code` | Next step |
|---|---|
| `VALIDATION_ERROR` | Fix fields/enums. Typed get/update type mismatch is this. |
| `ID_CONFLICT` | Evidence/gap/link ID conflicts within the row; inspect `current`. |
| `REVISION_CONFLICT` | GET `current`, merge, retry with new `revision`. |
| `REFERENCE_NOT_FOUND` | Fix target/evidence/gap ids. Do not invent them. |
| `SCOPE_MISMATCH` | Different repo/snapshot/scene; make a new row. |
| `STALE_DEPENDENCY` | Re-read the dependency at its current revision. |
| `INVALID_ASSESSMENT` | Add this-row evidence or keep `unknown`. |

## Hunt flow

1. `list-gates --file` / `list-sinks --file` (or `get-gate --id`) before analyzing.
2. Create unknown rows (`create-gate`, `create-sink`, …).
3. `append-evidence` for material; `append-gap` / `set-gap` for unknowns.
4. `set-verdict` only when this row's evidence plus assessment cover the statement.
5. Return the research result through the pipeline feedback field. Summarize
   material findings and unresolved questions as useful; do not declare
   exhaustion.
